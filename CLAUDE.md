# Diogram — контекст проекта для Claude

Мессенджер Diogram. Владелец и разработчик: Dimka999YT-Studio. Общаемся по-русски, дружелюбно и без лишней воды.

## Правила работы (важно)

1. **Никогда не сливай PR в `main` и не пушь в `main` без прямого разрешения владельца.** `main` выкатывается на боевой сервер. Любые изменения делаем в отдельной ветке, открываем pull request и спрашиваем «можно слить?».
2. Каждое изменение проверяем до публикации. Для Python: `python3 -m py_compile server.py db.py email_service.py`. Для клиента: проверить синтаксис inline-скрипта из `index.html` (`node --check`) и по возможности прогнать страницу в Chromium (Playwright) с подменённым API.
3. Честно говорим, что проверено, а что нет (живой базы Supabase у нас нет, SQL-функций в репозитории нет).
4. Секреты (ключи, пароли, токены) никогда не коммитим: только переменные окружения.
5. Правки `index.html` вносим точечно. Подмена файла целиком уже дважды стирала блок Frigdmant (коммиты `9719493` и `d2cc6bc`; между ними блок возвращали в `d7db072`). Если владелец присылает новую версию файла целиком, сначала сравни её с текущей (список функций и обработчиков) и скажи, что пропало.

## Стек и файлы

- `server.py`: Flask-API (`/api/*`), JWT (HS256, 30 дней), загрузки файлов, ИИ-бот Дио (Groq, модель `llama-3.3-70b-versatile`, id бота `1000011`).
- `db.py`: все запросы к Supabase (supabase-py).
- `email_service.py`: отправка писем по SMTP. Сервер сам письма **не отправляет**: коды регистрации кладутся в таблицу `pending_codes`, а внешний воркер забирает их через `/api/worker/get_pending` с заголовком `X-Worker-Key` и отправляет.
- `index.html`: весь клиент одним файлом (HTML, CSS, JS), общение с сервером через `fetch` на `/api/*`, обновление опросом (`/api/poll`), без WebSocket.
- `Procfile`: `gunicorn server:app --workers 1 --threads 16` (Heroku-подобный хостинг, `$PORT`). Один процесс с потоками: так работают кэши, лимиты и «печатает…» в памяти. Больше процессов — только вместе с Redis.

## Переменные окружения

`SUPABASE_URL`, `SUPABASE_KEY`, `JWT_SECRET`, `WORKER_KEY`, `GROQ_API_KEY`, `SMTP_EMAIL`, `SMTP_PASSWORD`, `TRUSTED_PROXIES` (число прокси перед приложением; по умолчанию 1, при запуске без прокси ставить 0).
Если `WORKER_KEY` пуст, воркер-эндпоинты закрыты для всех.

## Supabase

- Таблицы: `users`, `chats`, `chat_members`, `messages`, `channels`, `channel_subscribers`, `channel_messages`, `pending_codes`, `owned_usernames`, `frigdmant_listings`, `transactions`, `reports`, `photo_uploads`, `file_uploads`, `username_changes`, `user_sessions`, `frigdmant_bids`, `channel_poll_votes`, `message_reactions`, `channel_message_reactions`, `user_archive`.
- Бакеты хранилища: `avatars` (публичный) и `chat-photos` (вложения чатов; закрывается миграцией `20261031_chat_photos_private.sql`, применять только после выкатки кода с `/api/f/...`).
- Вложения: в `messages.attachment_url` лежит адрес вида `.../object/public/chat-photos/<имя>` (так же у старых сообщений). Перед выдачей участнику чата сервер подменяет его на `/api/f/<id сообщения>/<срок>/<подпись>` (`sign_attachments`: чат, опрос, ответы загрузок). Подпись HMAC от `JWT_SECRET`, срок 1–2 часа, ссылка ведёт 302 на подписанный URL хранилища (5 мин). Иконка монеты отдаётся сервером: `/assets/coin.jpg`.
- Миграции лежат в `supabase/migrations/` (с файлами отката). RLS включён на всех таблицах, у `anon`/`authenticated` прав нет: сервер ходит только под `service_role`.
- Каналы: к каналу можно привязать одну свою группу (`channels.linked_chat_id`): посты дублируются в группу (`messages.channel_post_id`), комментарии это сообщения группы с `reply_to_message_id`. Опросы: `channel_messages.poll` + `channel_poll_votes` (анонимные).
- Резерв юзернеймов: строки `owned_usernames` с `reserved = true` (держит owner, в коллекцию пользователя не попадают). Управление: вкладка «Резерв имён» в админке (только owner): добавить списком, выдать по ID, убрать. Выбор занятого ника даёт «Этот юзернейм занят пользователем @…» (`username_conflict`, действует и для каналов).
- Реакции: таблица `message_reactions` (PK message_id+user_id, одна реакция от пользователя, `chat_id` для выборки по чату), список эмодзи `REACTION_EMOJIS` в `server.py`. `POST /api/messages/<id>/react {emoji|null}`; сообщения и `/api/poll` отдают `reactions` и версию `rv` (счётчик в памяти на чат, как и «печатает…» — только при одном процессе); клиент шлёт `rv` и `rmin` и получает полный список, только если версия устарела. Миграция `20261101_message_reactions.sql` (откат рядом). Реакции в постах каналов: таблица `channel_message_reactions` (миграция `20261102_channel_reactions.sql`), `POST /api/channels/<id>/messages/<post>/react` (подписчик или владелец), реакции приходят в поле `reactions` каждого поста из `decorate_channel_messages` (канал и так перерисовывается опросом раз в 3 с, версии не нужны). Жесты: ПКМ / двойной клик / долгое нажатие (`bindRxGestures`), на сенсорных экранах выделение текста в сообщениях выключено.
- Копирование и пересылка сообщений: меню по ПКМ / двойному клику / долгому нажатию (то же, что у реакций) теперь содержит строку действий «📋 Копировать» (текст берётся из `el._raw`, `copyText`: Clipboard API, запасной путь `execCommand`) и «↪ Переслать» (окно `modal-forward` со списком чатов и групп, без каналов). У постов каналов только копирование. `POST /api/messages/<id>/forward {chat_id}`: пересылаются только `text`, `photo`, `file` (игровые сообщения нельзя); доступ проверяется и к исходному чату, и к целевому (как при обычной отправке, включая «Никто не может писать мне»), лимит 20 за 10 с и 60 в минуту. Вложение копируется ссылкой на тот же файл в хранилище (повторной загрузки нет, квоты файлов и лимит фото не тратятся), клиенту отдаётся подписанная ссылка `/api/f/...`. Метка пересылки: текст начинается с невидимого `FWD_MARK` (U+2063) и строки «↪ Переслано от Имя»; метку ставит только сервер, `strip_fwd_mark` вырезает её из текста сообщений и подписей к фото, иначе можно было бы подделать «переслано от @owner». Пересылка пересланного сохраняет первоначального автора. В списке чатов превью пересланного показывается как «↪ текст». Отдельной колонки в `messages` нет, миграция не нужна.
- Архив чатов: таблица `user_archive` (PK user_id+kind+target_id, kind `chat` для личных чатов и групп, `channel` для каналов; у каждого пользователя свой). `POST /api/archive {type, id, archived}` (проверка доступа, лимит 1000 и 60 запросов/мин), `/api/all_list` отдаёт всем элементам флаг `archived`; без таблицы архив пуст. Архивный чат остаётся в архиве и при новых сообщениях (на строке «📦 Архив» показана сумма непрочитанных). Клиент: ПКМ / долгое нажатие на чате в списке (`showListMenu`), строка «Архив» открывает `listView = "archive"`. Миграция `20261102_chat_archive.sql`.
- Видео-аватарки: только `owner` и `developer` (`VIDEO_AVATAR_ROLES`), через тот же `/api/upload/avatar`: MP4 (H.264) или WebM до 10 МБ и до 60 секунд, формат определяется по содержимому (`sniff_video`: для MP4 подходит любой бренд `ftyp`, кроме картинок HEIF/AVIF, аудио M4A и QuickTime из `_NOT_VIDEO_BRANDS`; в ошибке показан тип файла), длительность читается из заголовка файла (`video_duration`: MP4 `moov/mvhd`, WebM `Segment/Info/Duration`; если длительность не прочиталась, например у фрагментированного MP4 или live-WebM, файл отклоняется), в бакет `avatars` кладётся как `video/mp4` / `video/webm`. Бакет `avatars` должен разрешать файлы не меньше 10 МБ (`storage.buckets.file_size_limit`). Клиент рисует видео вместо картинки через `avatarHtml` / `avatarEl` (без звука, по кругу); любые новые места с `avatar_url` выводим через них, а не через `<img>`. Обычным пользователям и модераторам видео нельзя; групповые и канальные аватарки остаются картинками.
- Сезонная игра (аккаунт `@Play`, id `GAME_BOT_ID = 1000014`): любое сообщение ему в личном чате получает ответ-анонс (`GAME_INVITE_TEXT`, тип сообщения `game_invite`, на клиенте рисуется с кнопкой «🎮 Играть»), не чаще раза в 5 минут на человека; в группах не отвечает. Сезон и конец игры (`GAME_SEASON`, сейчас 1 декабря 2026 00:00 МСК) задаются в `server.py`; после конца бот отвечает `GAME_ENDED_TEXT` без кнопки. `GET /api/game/state` отдаёт `active` и `ends_at`. Кнопка «Играть» открывает экран игры (`openGame`, `screen-game`): Играть / Топ 3 / Общее / Выход. Кнопка «Играть» ведёт в лобби и на карту (см. ниже).
  Экономика (`game.py`, миграция `20261103_game_tournament.sql`, сезон `autumn_2026`): облачка `game_players` (с карты `clouds_map` и из кейсов `clouds_case`, в топ идёт сумма), 5 игр в день по МСК (`game_daily`, `game_use_attempt`: сначала дневные, потом бонусные из кейса «Ещё 1 игра»), топ 3 `game_top` (только `role=user`, не забаненные, ничья: кто раньше набрал; сотрудники всегда вне топа). Кейсы `CASES` (Обычный 1 Di, Редкий 10, Легендарный 25, Осенька 50; шансы в процентах, сумма каждого 100, проверяется при импорте): ролл через `secrets`, Di списываются и начисляются атомарно, сбой выдачи после списания возвращает цену, закончившийся приз (юзернейм/секретка) не открывается и Di не списывает; журнал `game_case_opens`. Эндпоинты `/api/game/me|top|cases|cases/open|prizes`; после конца сезона кейсы закрыты.
  Призы: `game_prize_usernames` (имя лежит в резерве владельца `owned_usernames.reserved`, при выдаче `game_take_username` передаёт его победителю и ставит номер выдачи `series_no`; из кейса выпадают по порядку `sort_no`, `pool=top` только награда за топ, выдаёт owner через `/api/admin/game/award`) и `game_prize_accounts` (твинки `почта:пароль`; админка проверяет, что аккаунт существует, пароль подходит и роль `user`). Призовой ник личный: `is_prize_username` блокирует продажу на Frigdmant, в окне юзернейма видно дату, номер и «выдано N/всего». Для призов разрешены имена с цифры (например `2FA`). Управление: вкладка «Призы турнира» в админке (только owner), пароли секреток админка не показывает. Призы топ-3: аккаунт-твинк, @Legend, 15 дней PDG (PDG выдаётся вручную).
  Выдача кейсов и склад (миграция `20261105_game_case_stock.sql`): таблицы `game_case_stock` (user_id+case_key → qty) и журнал `game_case_grants`, функции `game_case_add` / `game_case_take` (атомарно, в минус не уйти). Команда `/Case ID` в чате с @Play (только owner и developer, регистр не важен; остальным бот отвечает как обычно): бот присылает сообщение типа `game_case_give` (рисуется формой: кейс, количество 1–100, «Выдать», ID берётся из текста сообщения; тип сообщения ставит только сервер, пользователь его подделать не может), форма шлёт `POST /api/game/give_case {user_id, case, count}` (роль проверяется на сервере, лимит 30/мин), игрок получает сообщение от @Play «У тебя есть: N». В «Общее → Кейсы» у кейса видно «У вас есть: N» и две кнопки: открыть из запаса (`source: "inventory"`, Di не тратятся; сбой выдачи возвращает кейс на склад) или купить за Di. Открытие сопровождает анимация-рулетка (`gameRoll`, лента останавливается на призе, который сервер выбрал заранее; «Пропустить» показывает приз сразу); предметы рисуются плитками (`gameItemTile`: монета Di, SVG-облако, эмодзи; цвет рамки по шансу: до 2% золото, 5% фиолетовый, 10% синий, 30% зелёный, остальное серый). Без таблицы склада (миграция не применена) склад пуст, остальная игра работает.
  Карта и лобби (`game_world.py`, всё в памяти процесса, как «печатает…»; при нескольких воркерах не работает): до 5 лобби, в каждом до 5 игроков (последнее место держится для искателя), сотрудники (`STAFF_ROLES`) всегда искатели, игры не тратят и в топе не участвуют, пользователи прячутся. Раунд стартует через 12 с, когда в лобби есть искатель и хоть один прячущийся (при полном лобби через 3 с); попытка (`game_use_attempt`) списывается при старте раунда, у кого её нет, того убирают. Лобби живёт один раунд (45 с на показ итогов); в момент списания попыток лобби закрыто для входа (`state="starting"`), лобби, где у всех игроков давно нет тиков, освобождается само. Раунд 5 минут, первые 8 с искатель стоит. Карта 1400×900 (`MAP`, одинакова для всех, делается из фиксированного seed): деревья непроходимы, кусты скрывают прячущегося (видно только вплотную, 70), туман 260 (сервер не отдаёт дальше; пойманные наблюдают без тумана), 4 коробки: клик и 10 с рядом с коробкой, сломанная снимает у искателя 25 из 100 HP, 4 коробки = искатель уничтожен, прячущиеся побеждают; на карте 9 облачков; искатель ловит касанием (30), пойманный теряет облачка раунда. Итоги: победа прячущихся (время вышло, искатель уничтожен или ушёл) даёт каждому прячущемуся, включая пойманных, +1 облачко, но не больше 10 за игру; победа искателей облачек не даёт; облачка зачисляет `game_add` в `clouds_map`. Сервер авторитетен: клиент шлёт `POST /api/game/tick {dx, dy, brk}` примерно 3,5 раза в секунду (путь в `CACHE_KEEP_PATHS`), мир досчитывается лениво при каждом тике (шаги по 50 мс, не больше 2 с за раз), игрок без тиков 15 с выбывает. Эндпоинты: `/api/game/lobbies|map|join|tick|leave`. Клиент (`gameRunStart`, `grDraw`): canvas, предсказание своего движения, стрелки/WASD или сенсорный джойстик, кнопка «Ломать» (E/пробел). Все константы (скорости, радиусы, время) вверху `game_world.py`.
  Чат лобби (`game_world.py`: `Lobby.say`, `GameHub.chat`; константы `CHAT_MAX_LEN` 100, `CHAT_KEEP` 30, `CHAT_SEND` 12): сообщение видят все игроки лобби, включая пойманных и искателей, хранится в памяти лобби (как «печатает…»), до 100 символов, пробелы схлопываются, `FWD_MARK` вырезается. `POST /api/game/chat {text}` (3 за 4 с и 20 в минуту на игрока, вне лобби 400; путь в `CACHE_KEEP_PATHS`), последние 12 сообщений приходят в `chat` каждого ответа `/api/game/tick`, клиент дедуплицирует по `id` (`grChatRender`). Кнопка 💬 в шапке игры открывает строку ввода (`grChatOpen`), пока она открыта WASD игнорируются, Esc закрывает; сообщения рисуются через `textContent` и гаснут через 12 с. Таблиц и миграций нет.
  Журнал чата (`game_chatlog.py`, миграция `20261125_game_chat_log.sql`, откат рядом): каждое сообщение чата лобби пишется в `game_chat_log` (сезон, лобби, id, имя, роль, текст) в фоновом потоке, ошибки записи не ломают чат; хранится 30 дней (сервер чистит раз в час при записи). Читает только owner: `GET /api/admin/game/chat?days=1|7|30` отдаёт `{text, count}` (txt, МСК), в админке «🎮 Игра» три кнопки «⬇» скачивают файл. Без миграции чат работает, журнал пуст, выгрузка отвечает ошибкой. Выгрузку в приватный репозиторий `Secret-Diogram-` делает Claude по просьбе владельца (чтение таблицы через Supabase, файл в `chatlogs/`). В политике конфиденциальности про журнал чата пока ничего нет.
  Радужные круги (`rainbow.py`, миграция `20261126_rainbow_circles.sql`, откат рядом): валюта чата игр, 1 круг за сообщение (`CHAT_COST`), сотрудники (`STAFF_ROLES`) пишут бесплатно. Таблицы `rainbow_wallets` (круги, `free_used`), `rainbow_log`; SQL-функции `rainbow_buy(p_buyer, p_target, ...)` (под блокировкой кошельков списывает Di у покупателя дробно, баланс `numeric`, и зачисляет круги получателю; `rainbow_log.target_id`), `rainbow_spend` (остаток или -1), `rainbow_refund`. Магазин (`PACKS`): 1 круг (первый бесплатно, один раз на аккаунт, потом 0,99 Di), 50 за 40 Di (хит, −19%), 100 за 72 (−27%), 1000 за 700 (мега, −29%); скидка считается от 0,99 за штуку (`discount`). Покупка для себя или друга: `POST /api/rainbow/buy {pack, username}` (10/мин), юзернейм обязателен, подходит активный ник (`get_user_by_username`) или коллекционный (`get_collection_holder_user`, резерв не считается), забаненный получатель = 404; бесплатный одиночный круг принадлежит покупателю (`free_used`), его можно подарить, а себе купить платно. `GET /api/rainbow/me`. `/api/game/chat`: проверка лобби и текста, списание круга, при отказе чата круг возвращается; нет кругов = 402 `need_circles`; сбой базы при списании пропускает сообщение (чат не блокируется). Клиент: меню игры «🌈 Радужные круги» (`gameRainbow`, радужный блестящий фон, `rbIcon` рисует иконку SVG), остаток в строке чата (`gp-chat-rb`). Круги не сезонные, не сгорают. Транзакции в `transactions` не пишутся (там `amount` bigint), история в `rainbow_log`. В политике конфиденциальности добавлен раздел 12 про журнал чата.

- Сессии: вход и подтверждение регистрации создают строку в `user_sessions` (устройство из User-Agent, максимум 20 на пользователя), её id лежит в JWT (`sid`). Токен без `sid` (выданный до сессий) работает до конца срока. Удалил сессию (настройки, «завершить все остальные», выход) — токен сразу перестаёт работать (401 `session_revoked`, клиент выходит). Проверка сессии кэшируется на 10 с и сбрасывается любой записью. Токен без `sid` при открытии списка сессий (`GET /api/sessions`) или «завершить все остальные» получает новую сессию и новый токен в поле `token` (`ensure_current_session`), клиент сохраняет его: раньше у такого токена «это устройство» не находилось, а `revoke_others` с пустым `keep` удалял все сессии аккаунта, при этом сам старый токен продолжал работать. Теперь `delete_other_sessions` без `keep` отказывает, а при сбое создания сессии `revoke_others` отвечает 500 и ничего не удаляет. Старые токены без `sid` других устройств отозвать по-прежнему нельзя: они живут до конца своих 30 дней.

- Регистрация без потери номеров ID (миграция `20261122_create_user_atomic.sql`, откат рядом): `db.create_user` вызывает SQL-функцию `create_user_atomic` (блокировка по почте и нику, проверка и вставка одним вызовом). Занятая почта или ник отсекаются до `nextval`, поэтому двойное нажатие или две параллельные регистрации не сжигают номер в `users_id_seq` (раньше проверка и insert были раздельными, insert падал на уникальном индексе, а счётчик уже двигался). Без функции (миграция не применена) работает прежний insert, сбой связи вторым insert не повторяется. Пропуски в ID остаются от ручных удалений аккаунтов и других сбоев: счётчик Postgres не откатывается, и переиспользовать ID нельзя (JWT хранит id, старый токен открыл бы чужой аккаунт).

## Что важно помнить в коде

- Текущий пользователь берётся через `get_current_user()` (кэш на запрос в `flask.g`); забаненные блокируются в `before_request` на всех `/api/*`, кроме входа, регистрации и `/api/me`.
- Ввод разбираем через `json_body`, `str_field`, `to_int`, `int_arg`. Не вызываем `int()` и `.strip()` на сырых данных.
- В клиенте `escapeHtml` не экранирует кавычки. Для значений в атрибутах используем `escapeAttr`, а пользовательские данные не вставляем в inline `onclick`.
- Скорость: короткие кэши в памяти (`_user_cache` 5 с, чат 30 с, членство 10 с); любой изменяющий запрос (кроме `/api/send`, `/api/typing`, `/api/poll`, чтения, голосов и комментариев) сбрасывает кэши. `last_seen` пишется не чаще раза в 20 с. Опрос чата идёт по `after_id`, клиент опрашивает цепочкой (следующий запрос после ответа) и не рисует сообщение с уже показанным id. Отправка идемпотентна по `client_id` (уникальный индекс в `messages`). Списки чатов/каналов собираются SQL-функциями `chat_summaries` и `channel_summaries` (миграция `20261027_perf.sql`, есть запасной путь без них).
- Защита: заголовки (CSP только `self` для запросов и адрес нашего проекта `SUPABASE_URL` для картинок/аудио (без `SUPABASE_URL` запасной вариант `*.supabase.co`), запрет встраивания, nosniff, HSTS по https) ставит `security_headers`; общий лимит 600 запросов/мин на аккаунт (`API_RATE_PER_MIN`, ответ 429 `rate_limited`), поиск 30/мин; необработанные ошибки отдают клиенту только общий текст (подробности в лог). Группы: до 20 своих и 5 новых в час (сотрудники без лимита), выход `POST /api/chats/<id>/leave` (владелец выходит — права получает самый давний участник; квоту 20 групп занимают только группы, где владелец ещё участник; владелец группы, привязанной к каналу, выйти не может).
- Лимиты (`check_rate_limit`) хранятся в памяти процесса: при нескольких воркерах gunicorn считаются отдельно в каждом.
- Роли: `owner`, `developer`, `moderator`, `user`.
