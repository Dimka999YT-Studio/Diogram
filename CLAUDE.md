# Diogram — контекст проекта для Claude

Мессенджер Diogram. Владелец и разработчик: Dimka999YT-Studio. Общаемся по-русски, дружелюбно и без лишней воды.

## Правила работы (важно)

1. **Никогда не сливай PR в `main` и не пушь в `main` без прямого разрешения владельца.** `main` выкатывается на боевой сервер. Любые изменения делаем в отдельной ветке, открываем pull request и спрашиваем «можно слить?».
2. Каждое изменение проверяем до публикации. Для Python: `python3 -m py_compile server.py db.py email_service.py`. Для клиента: проверить синтаксис inline-скрипта из `index.html` (`node --check`) и по возможности прогнать страницу в Chromium (Playwright) с подменённым API.
3. Честно говорим, что проверено, а что нет (живой базы Supabase у нас нет, SQL-функций в репозитории нет).
4. Секреты (ключи, пароли, токены) никогда не коммитим: только переменные окружения.
5. Правки `index.html` вносим точечно. Подмена файла целиком уже дважды стирала блок Frigdmant (коммиты `9719493` и `d2cc6bc`; между ними блок возвращали в `d7db072`). Если владелец присылает новую версию файла целиком, сначала сравни её с текущей (список функций и обработчиков) и скажи, что пропало.

## Стек и файлы

- `server.py`: Flask-API (`/api/*`), JWT (HS256, 30 дней), загрузки файлов, ИИ-бот Дио (Groq, модель `llama-3.3-70b-versatile`, id бота `1000011`).
- `db.py`: все запросы к Supabase (supabase-py).
- `email_service.py`: отправка писем по SMTP. Сервер сам письма **не отправляет**: коды регистрации кладутся в таблицу `pending_codes`, а внешний воркер забирает их через `/api/worker/get_pending` с заголовком `X-Worker-Key` и отправляет.
- `index.html`: весь клиент одним файлом (HTML, CSS, JS), общение с сервером через `fetch` на `/api/*`, обновление опросом (`/api/poll`), без WebSocket.
- `Procfile`: `gunicorn server:app --workers 1 --threads 16` (Heroku-подобный хостинг, `$PORT`). Один процесс с потоками: так работают кэши, лимиты и «печатает…» в памяти. Больше процессов — только вместе с Redis.

## Переменные окружения

`SUPABASE_URL`, `SUPABASE_KEY`, `JWT_SECRET`, `WORKER_KEY`, `GROQ_API_KEY`, `SMTP_EMAIL`, `SMTP_PASSWORD`, `TRUSTED_PROXIES` (число прокси перед приложением; по умолчанию 1, при запуске без прокси ставить 0).
Если `WORKER_KEY` пуст, воркер-эндпоинты закрыты для всех.

## Supabase

- Таблицы: `users`, `chats`, `chat_members`, `messages`, `channels`, `channel_subscribers`, `channel_messages`, `pending_codes`, `owned_usernames`, `frigdmant_listings`, `transactions`, `reports`, `photo_uploads`, `file_uploads`, `username_changes`, `user_sessions`, `frigdmant_bids`, `channel_poll_votes`, `message_reactions`, `channel_message_reactions`, `user_archive`.
- Бакеты хранилища: `avatars` (публичный) и `chat-photos` (вложения чатов; закрывается миграцией `20261031_chat_photos_private.sql`, применять только после выкатки кода с `/api/f/...`).
- Вложения: в `messages.attachment_url` лежит адрес вида `.../object/public/chat-photos/<имя>` (так же у старых сообщений). Перед выдачей участнику чата сервер подменяет его на `/api/f/<id сообщения>/<срок>/<подпись>` (`sign_attachments`: чат, опрос, ответы загрузок). Подпись HMAC от `JWT_SECRET`, срок 1–2 часа, ссылка ведёт 302 на подписанный URL хранилища (5 мин). Иконка монеты отдаётся сервером: `/assets/coin.jpg`.
- Миграции лежат в `supabase/migrations/` (с файлами отката). RLS включён на всех таблицах, у `anon`/`authenticated` прав нет: сервер ходит только под `service_role`.
- Каналы: к каналу можно привязать одну свою группу (`channels.linked_chat_id`): посты дублируются в группу (`messages.channel_post_id`), комментарии это сообщения группы с `reply_to_message_id`. Опросы: `channel_messages.poll` + `channel_poll_votes` (анонимные).
- Резерв юзернеймов: строки `owned_usernames` с `reserved = true` (держит owner, в коллекцию пользователя не попадают). Управление: вкладка «Резерв имён» в админке (только owner): добавить списком, выдать по ID, убрать. Выбор занятого ника даёт «Этот юзернейм занят пользователем @…» (`username_conflict`, действует и для каналов).
- Реакции: таблица `message_reactions` (PK message_id+user_id, одна реакция от пользователя, `chat_id` для выборки по чату), список эмодзи `REACTION_EMOJIS` в `server.py`. `POST /api/messages/<id>/react {emoji|null}`; сообщения и `/api/poll` отдают `reactions` и версию `rv` (счётчик в памяти на чат, как и «печатает…» — только при одном процессе); клиент шлёт `rv` и `rmin` и получает полный список, только если версия устарела. Миграция `20261101_message_reactions.sql` (откат рядом). Реакции в постах каналов: таблица `channel_message_reactions` (миграция `20261102_channel_reactions.sql`), `POST /api/channels/<id>/messages/<post>/react` (подписчик или владелец), реакции приходят в поле `reactions` каждого поста из `decorate_channel_messages` (канал и так перерисовывается опросом раз в 3 с, версии не нужны). Жесты: ПКМ / двойной клик / долгое нажатие (`bindRxGestures`), на сенсорных экранах выделение текста в сообщениях выключено.
- Архив чатов: таблица `user_archive` (PK user_id+kind+target_id, kind `chat` для личных чатов и групп, `channel` для каналов; у каждого пользователя свой). `POST /api/archive {type, id, archived}` (проверка доступа, лимит 1000 и 60 запросов/мин), `/api/all_list` отдаёт всем элементам флаг `archived`; без таблицы архив пуст. Архивный чат остаётся в архиве и при новых сообщениях (на строке «📦 Архив» показана сумма непрочитанных). Клиент: ПКМ / долгое нажатие на чате в списке (`showListMenu`), строка «Архив» открывает `listView = "archive"`. Миграция `20261102_chat_archive.sql`.
- Видео-аватарки: только `owner` и `developer` (`VIDEO_AVATAR_ROLES`), через тот же `/api/upload/avatar`: MP4 (H.264) или WebM до 10 МБ и до 60 секунд, формат определяется по содержимому (`sniff_video`: для MP4 подходит любой бренд `ftyp`, кроме картинок HEIF/AVIF, аудио M4A и QuickTime из `_NOT_VIDEO_BRANDS`; в ошибке показан тип файла), длительность читается из заголовка файла (`video_duration`: MP4 `moov/mvhd`, WebM `Segment/Info/Duration`; если длительность не прочиталась, например у фрагментированного MP4 или live-WebM, файл отклоняется), в бакет `avatars` кладётся как `video/mp4` / `video/webm`. Бакет `avatars` должен разрешать файлы не меньше 10 МБ (`storage.buckets.file_size_limit`). Клиент рисует видео вместо картинки через `avatarHtml` / `avatarEl` (без звука, по кругу); любые новые места с `avatar_url` выводим через них, а не через `<img>`. Обычным пользователям и модераторам видео нельзя; групповые и канальные аватарки остаются картинками.
- Сезонная игра (аккаунт `@Play`, id `GAME_BOT_ID = 1000014`): любое сообщение ему в личном чате получает ответ-анонс (`GAME_INVITE_TEXT`, тип сообщения `game_invite`, на клиенте рисуется с кнопкой «🎮 Играть»), не чаще раза в 5 минут на человека; в группах не отвечает. Сезон и конец игры (`GAME_SEASON`, сейчас 1 декабря 2026 00:00 МСК) задаются в `server.py`; после конца бот отвечает `GAME_ENDED_TEXT` без кнопки. `GET /api/game/state` отдаёт `active` и `ends_at`. Кнопка «Играть» открывает экран игры (`openGame`, `screen-game`): Играть / Топ 3 / Общее / Выход. Карта и лобби будут отдельным PR, пока «Играть» честно пишет, что карта скоро откроется.
  Экономика (`game.py`, миграция `20261103_game_tournament.sql`, сезон `autumn_2026`): облачка `game_players` (с карты `clouds_map` и из кейсов `clouds_case`, в топ идёт сумма), 5 игр в день по МСК (`game_daily`, `game_use_attempt`: сначала дневные, потом бонусные из кейса «Ещё 1 игра»), топ 3 `game_top` (только `role=user`, не забаненные, ничья: кто раньше набрал; сотрудники всегда вне топа). Кейсы `CASES` (Обычный 1 Di, Редкий 10, Легендарный 25, Осенька 50; шансы в процентах, сумма каждого 100, проверяется при импорте): ролл через `secrets`, Di списываются и начисляются атомарно, сбой выдачи после списания возвращает цену, закончившийся приз (юзернейм/секретка) не открывается и Di не списывает; журнал `game_case_opens`. Эндпоинты `/api/game/me|top|cases|cases/open|prizes`; после конца сезона кейсы закрыты.
  Призы: `game_prize_usernames` (имя лежит в резерве владельца `owned_usernames.reserved`, при выдаче `game_take_username` передаёт его победителю и ставит номер выдачи `series_no`; из кейса выпадают по порядку `sort_no`, `pool=top` только награда за топ, выдаёт owner через `/api/admin/game/award`) и `game_prize_accounts` (твинки `почта:пароль`; админка проверяет, что аккаунт существует, пароль подходит и роль `user`). Призовой ник личный: `is_prize_username` блокирует продажу на Frigdmant, в окне юзернейма видно дату, номер и «выдано N/всего». Для призов разрешены имена с цифры (например `2FA`). Управление: вкладка «Призы турнира» в админке (только owner), пароли секреток админка не показывает. Призы топ-3: аккаунт-твинк, @Legend, 15 дней PDG (PDG выдаётся вручную).
  Для нового сезона поменять тексты, дату и `SEASON` в `game.py`.
- Сессии: вход и подтверждение регистрации создают строку в `user_sessions` (устройство из User-Agent, максимум 20 на пользователя), её id лежит в JWT (`sid`). Токен без `sid` (выданный до сессий) работает до конца срока. Удалил сессию (настройки, «завершить все остальные», выход) — токен сразу перестаёт работать (401 `session_revoked`, клиент выходит). Проверка сессии кэшируется на 10 с и сбрасывается любой записью.
- SQL-функции (RPC), описаны в миграции `20261026_frigdmant_and_security.sql`: `spend_balance_atomic`, `add_balance_atomic`, `buy_username_atomic`, `place_bid_atomic`, `close_auction_atomic`.

## Что важно помнить в коде

- Текущий пользователь берётся через `get_current_user()` (кэш на запрос в `flask.g`); забаненные блокируются в `before_request` на всех `/api/*`, кроме входа, регистрации и `/api/me`.
- Ввод разбираем через `json_body`, `str_field`, `to_int`, `int_arg`. Не вызываем `int()` и `.strip()` на сырых данных.
- В клиенте `escapeHtml` не экранирует кавычки. Для значений в атрибутах используем `escapeAttr`, а пользовательские данные не вставляем в inline `onclick`.
- Скорость: короткие кэши в памяти (`_user_cache` 5 с, чат 30 с, членство 10 с); любой изменяющий запрос (кроме `/api/send`, `/api/typing`, `/api/poll`, чтения, голосов и комментариев) сбрасывает кэши. `last_seen` пишется не чаще раза в 20 с. Опрос чата идёт по `after_id`, клиент опрашивает цепочкой (следующий запрос после ответа) и не рисует сообщение с уже показанным id. Отправка идемпотентна по `client_id` (уникальный индекс в `messages`). Списки чатов/каналов собираются SQL-функциями `chat_summaries` и `channel_summaries` (миграция `20261027_perf.sql`, есть запасной путь без них).
- Защита: заголовки (CSP только `self` для запросов и `*.supabase.co` для картинок/аудио, запрет встраивания, nosniff, HSTS по https) ставит `security_headers`; общий лимит 600 запросов/мин на аккаунт (`API_RATE_PER_MIN`, ответ 429 `rate_limited`), поиск 30/мин; необработанные ошибки отдают клиенту только общий текст (подробности в лог). Группы: до 20 своих и 5 новых в час (сотрудники без лимита), выход `POST /api/chats/<id>/leave` (владелец выходит — права получает самый давний участник; владелец группы, привязанной к каналу, выйти не может).
- Лимиты (`check_rate_limit`) хранятся в памяти процесса: при нескольких воркерах gunicorn считаются отдельно в каждом.
- Роли: `owner`, `developer`, `moderator`, `user`.
